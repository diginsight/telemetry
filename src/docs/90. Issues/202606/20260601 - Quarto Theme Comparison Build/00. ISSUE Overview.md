## 📝 DESCRIPTION

The Diginsight Telemetry documentation site is built with Quarto and currently uses the `cosmo` Bootswatch theme (light + dark) with custom SCSS overrides for the navbar palette. Choosing a long-term theme requires actually seeing the full site rendered in every candidate theme — not just inspecting palette swatches — because typography, sidebar density, callout boxes, code blocks, and the announcement banner all react differently per theme.

The task: build the **same site** once per available Bootswatch theme, side by side, so styles can be contrasted on real content (Home, Concepts, Advanced, Reference, About, Changelogs, Issues) and a deliberate choice can be made.

### Error Message
N/A — this is an enhancement task. No defect; no exception was thrown. The starting state simply did not allow visual A/B comparison of themes.

### Impact
- Theme selection had to be done blind, by reading Bootswatch docs and guessing how each palette would interact with the Diginsight content (deep sidebar, many callouts, long code blocks).
- Switching themes manually in [_quarto.yml](../../../../_quarto.yml) and re-rendering each time clobbers the published `docs/` output and is too slow (~1–2 min per render) to iterate.
- No way to compare two themes side-by-side in the browser without two manual renders into conflicting output directories.

## 🔬 ANALYSIS

### Root Cause Analysis

#### Why a one-shot loop is not enough
Three concerns made this more than "render in a `for` loop":

1. **Output isolation.** The default render writes to `docs/`, which is the published site. Theme experiments must not touch it.
2. **Config swap safety.** The theme is hard-coded in `_quarto.yml`. A failed render mid-loop would leave the repo with the wrong theme committed. Any change must be reverted in a `try/finally`.
3. **Comparison ergonomics.** Twenty-five independent sites are not a comparison — they're just 25 sites. A landing page is needed to switch between them in a single browser window.

#### Why custom navbar SCSS had to be stripped
[theme-light.scss](../../../../theme-light.scss) and [theme-dark.scss](../../../../theme-dark.scss) force navbar colours (`#c78e3c` / `#8b6129`). Leaving them in the variant builds would have rendered every theme with the same orange navbar — masking exactly the difference being evaluated. The patch therefore replaces the full `theme:` block (which inherits the SCSS list) with a plain `theme: <name>` for each variant.

### Impact Assessment

| Category | Impact | Severity |
|----------|--------|----------|
| **Functionality** | None — published site untouched; experiment is fully sandboxed | Low |
| **Repo state safety** | `_quarto.yml` is mutated mid-build but restored in `finally` | Low (mitigated) |
| **Disk usage** | 25 × ~25 MB ≈ 600 MB in `docs-themes/` | Low |
| **Render wall time** | ~25 min serial for full matrix | Low |

### Affected Workflows
1. ✅ **Production publish** ([quarto-publish.yml](../../../../.github/workflows/quarto-publish.yml)): unaffected — it still runs `quarto render` against the committed `_quarto.yml` and uploads `docs/`.
2. ✅ **Local theme evaluation** (new): supported by `build-theme-previews.ps1` + `docs-themes/index.html`.
3. ⚠️ **Parallel rendering**: not supported by the current script. Requires N isolated working copies (junctioned `src/` and `_extensions/`) — see [Future Improvements](#improvements-for-future).

## ✅ SOLUTION IMPLEMENTED

### Fix Overview
Add a PowerShell driver script that:

1. Backs up [_quarto.yml](../../../../_quarto.yml) in memory.
2. For each theme in a 25-entry table, regex-replaces the `format.html.theme` block with a flat `theme: <name>` (deliberately dropping the custom navbar SCSS so each variant shows its native palette).
3. Runs `quarto render --output-dir docs-themes/<theme> --quiet`.
4. In a `finally` block, unconditionally writes the original YAML back — so an interrupted run or a Quarto failure cannot leave the repo with a broken config.
5. Emits a `docs-themes/index.html` landing page with a CSS grid of theme cards (left) and an iframe preview pane (right).

### Code Changes

#### 1. New driver script
**Location:** [build-theme-previews.ps1](../../../../build-theme-previews.ps1) (repo root)

Key features:
- Parameterised: `-Themes`, `-OutRoot`, `-SkipExisting`.
- 25-entry theme table tagged `light` / `dark` for badge rendering.
- Regex patches only the multi-line `theme:` block — leaves the rest of `_quarto.yml` byte-identical.
- `try/finally` guarantees YAML restoration even on Ctrl+C or render failure.
- Per-theme stopwatch, exit-code check, end-of-run summary table.

#### 2. Generated comparison page
**Location:** `docs-themes/index.html` (generated by the script; **not** committed)

Two-pane layout:
- **Left aside (`280px`)**: CSS-grid card list, light/dark badge per theme, hover affordance.
- **Right `<main>`**: toolbar + `<iframe name="preview">` defaulting to `cosmo/Index.html`.
- All theme cards `target="preview"` so a click swaps the iframe; middle-click still opens in a new tab for full-window comparison.

### Solution Features

#### ✅ Sandboxed from the published site
Variants render to `docs-themes/<theme>/`, never touching `docs/`. The GitHub Pages workflow is unaffected.

#### ✅ Crash-safe config mutation
`_quarto.yml` is restored from the in-memory backup in `finally`. Interruption or render failure cannot corrupt the committed config.

#### ✅ Fair visual comparison
Custom navbar SCSS is stripped per variant, so each theme renders with its native Bootswatch palette. The user-confirmed default; alternative ("keep overrides") is documented but not enabled.

#### ✅ Resumable
`-SkipExisting` skips any theme whose `Index.html` already exists, so interrupted runs continue where they stopped without re-rendering.

## 🎓 LESSONS LEARNED

### What Went Wrong
1. **First attempt loaded large attached images unnecessarily** — image attachments were inspected by the assistant despite the request being purely about repo/code. Cost: model image budget, time. Fix: rely on text-only repo reads.
2. **Initial `--quiet` Quarto output looked stalled** — with `--quiet` and a long deno startup, the first ~90 s show no terminal output, which is indistinguishable from a hang without checking `Get-Process`. Future scripts should keep a brief heartbeat (e.g. printing the current step's file count progress) instead of silencing everything.

### What Went Right
1. **One-theme smoke test before the matrix** — running `-Themes flatly` first validated the regex patch, output-dir flag, and `try/finally` restore in 2 min, avoiding wasted work on a broken loop.
2. **`try/finally` for config mutation** — restored `_quarto.yml` even though the run completed normally; would have saved the repo from a corrupted commit on any failure mid-loop.
3. **Targeted, non-destructive regex** — replaced exactly the `theme:` block without disturbing whitespace, comments, or any other YAML key, so `git diff _quarto.yml` is empty after the run.
4. **Decided scope with the user before launching the 26-min build** — `vscode_askQuestions` confirmed "all 25" and "strip custom SCSS" before committing to the long run.

### Improvements for Future
1. **Parallelize via junctioned worktrees.** Per-theme working copies (junction the heavy read-only `src/` and `_extensions/`, copy only the small root configs) eliminate the shared-config and shared-`.quarto/` cache contention. Combined with `Start-ThreadJob -ThrottleLimit 4` this should cut wall time ~3×.
2. **Drop a comparison snapshot artifact**. Headless Playwright over `docs-themes/index.html` could produce a single `comparison.pdf` or stitched PNG of all theme home-pages for offline review and PR attachment.
3. **Surface render progress without `--quiet`** — tee Quarto output through a per-theme log file so the console shows just a one-line heartbeat but full logs are available on failure.
